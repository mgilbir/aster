# 0013: Invalid Vega-Lite and Vega input fails where upstream throws

**Status:** accepted, 2026-10-12; extended to Vega, 2026-10-19.

## Context

Vega-Lite's compiler validates little. A value of the wrong type in a specification mostly reaches code that uses it as the right type, and the compilation then fails with the TypeError JavaScript raises: `spec.layer.map is not a function` for `"layer": {}`, `Cannot use 'in' operator to search for 'scale' in a` for a channel defined as `"a"` under 5.8. Aster's compiler read such values leniently instead: `Items()` of an object is empty, `AsString()` of a number is its text. So `"layer": {}`, `"transform": {}`, `"params": 1` or the legacy `"in"` predicate compiled to a blank chart with a nil error, where upstream fails (audit findings C49 and C50; a differential of 1,500 type-confused corpus specs found about 80 such mutants). The project had no stated policy on schema-invalid input (audit open question 4), and ADR 0006 already holds that a chart must not silently lose what the specification asked for.

## Decision

- **Where upstream throws, aster returns an error.** For each Vega-Lite version aster follows (6.4.3, and 5.8.0 behind `WithVegaLiteVersion`), a value that makes upstream's compiler throw makes aster's fail too, at the operation where upstream's would. Both versions are held to it: 5.8's predicates use JavaScript's `in` operator where 6.4 uses `hasProperty`, so 5.8 rejects primitives in many more places, and aster's 5.8 mode does as well.
- **The error names what was wrong.** Where upstream throws an Error of its own (`Invalid field type "undefined".`) aster uses its message. Where upstream fails with a JavaScript TypeError, aster's message is that TypeError's text (`spec.layer.map is not a function`), which names the property, so a message can be matched against upstream's.
- **Where upstream accepts a value, aster reproduces what it does with it**, including the lenient readings JavaScript gives it: a string where a list of repeat values is expected is iterated by character, as `for…of` does; a primitive channel definition in 6.4 becomes `{value: …}` with upstream's warning. Strictness beyond upstream's would make valid-in-practice specifications fail where Vega-Lite renders them.
- **`TestVegaLiteTypeConfusionMatchesNode` is the guard.** It replaces one value of a corpus specification with a value of another type and compiles the mutant here and in node with both versions. Where node throws, the engine must fail; where node compiles, the engine must compile; where both compile, the engine's warnings must be node's, in order and count, and its compiled Vega must be node's exactly (as JSON, key order included; nothing is normalised, as upstream's compiler is deterministic under the oracle's pinned clock). Node answers as a fresh process would (the oracle replaces a process whose built-ins upstream changed). It has no allowlist (its vocabulary, derived from the value it replaces since 2026-10-19, is ADR 0026's): with the default seed (1,500 mutants) and seeds 7, 11, 13, 17, 43, 47, 53, 59, 61 and 67 (10,000 each) and 20740 (784,629, the nightly search's) it reports no difference. The search continues nightly with a new seed (the `typeconfusion` job of `.github/workflows/fuzz.yml`), and each divergence found becomes a mutant in `testdata/typeconfusion`, which `TestTypeConfusionRegressionsMatchNode` replays (docs/testing.md). `TestInvalidStructureMatchesNode` holds the structural slots (composition lists, repeat, transform, params, field type, channel definitions, the legacy `in` predicate) to node's answer, both its errors and its output.

## Why

Fidelity to upstream (ADR 0004) is the engine's first rule, and an error is part of upstream's output: a specification that fails in the Vega-Lite editor should not render as an empty chart here. Mirroring upstream rather than validating against the JSON schema keeps the two in step: a schema check would reject specifications upstream renders (the schema is stricter than the compiler) and accept ones it rejects.

## Consequences

- A behaviour change: specifications that compiled to a blank or partial chart now return an error, as they do upstream.
- Mirroring is per call site, so new code that reads a specification value must read it the way upstream does, including the TypeError where upstream's would raise one (`listOf`, `iterate`, `jsIn` and `varNameOf` in `internal/vegalite`).
- Mirroring reaches into JavaScript semantics the specification can observe: the `in` operator sees `Object.prototype` (and, for arrays, `Array.prototype`) members, so under 5.8 an aggregate `"toString"` or `"__proto__"` behaves as upstream's does; JSON output drops function values a specification can reach that way; `splitAccessPath` bounds its loop by the field's length before string conversion. `internal/jsval` marks such inherited values so the compiler can tell them from data.
- Upstream keeps state in plain objects keyed by names a specification chooses (a parse or a filter by field, an aggregate's measures, a selection's projections and components, `util.unique`'s seen set) and in constant tables it looks names up in, and the compiler reproduces what one upstream compilation does with them (`jsRealm` in `internal/vegalite/jsobject.go`, behind `omap`, the jsval-object maps and the table lookups): a field named after an `Object.prototype` member reads as present, assigning `"__proto__"` replaces the object's prototype or does nothing, and a write through such a member lands on the built-in. So a data column named `constructor` behaves as it does upstream, bug included: aggregating it (`{"field": "constructor", "aggregate": "distinct"}`) drops the measure, because `meas["constructor"] ??= {}` finds `Object` and the op is written there; and an aggregate of a field named `__proto__` writes its measures onto `Object.prototype`. Matching that is the rule (the output of a specification upstream compiles is upstream's); not matching it would make the same specification compile differently here and in the Vega-Lite editor.
- What a write onto a built-in leaves is kept for the rest of that compilation only, never in the process: node keeps it, so one compilation there can change the next one's output (the test oracle restarts such a process), and aster's compilations stay independent. The model covers the maps and tables above, and one read through a specification object: 5.8's `a['argmax']` and `a['argmin']` of an aggregate, which finds the Set an aggregate over a field named `__proto__` wrote there, so every later aggregate reads as an argmax over `[object Set]`, as upstream's does. Other reads of a polluted `Object.prototype` through a specification object of the same compilation are not modelled, and the Vega runtime is not affected by it (node's is: rendering the error band of `testdata/corpus/regress/error-band-over-a-field-named-proto.vl.json` overflows its stack, which `testdata/oracle-expect.txt` records).

## Extension to Vega (2026-10-19)

### Context

The decision above covered the Vega-Lite compiler only. The Vega parser and runtime had no stated policy (audit 2026-10-18, C48): they were lenient by accident in some places and strict in others. `"transform": {…}` given as an object rendered, where upstream fails with `data.transform.forEach is not a function`; a signal's DOM-event handler was never parsed, so `"update": "nosuch + 1"` rendered where upstream fails with `Unrecognized signal name`; `"type": ["linear"]` made a linear scale where upstream fails; and where upstream renders, the engine often refused (`"nice": [true]`, a mark `type` that is a list, a `clip` path given as a number) or drew something else (a value reference upstream compiles to JavaScript source the engine evaluated otherwise, a width given as text that upstream concatenates into the view size).

### Decision

- **The same rule for Vega (the owner's decision of 2026-10-18).** Where upstream Vega throws on a specification, at parse, while the view is made, while the dataflow runs, or while the SVG is written, the engine fails; where upstream renders, the engine renders what it renders. Exact parity both ways, as for Vega-Lite.
- **The parser reads a value as vega-parser's JavaScript reads it.** `for (k in v)` and vega-util's `extend` enumerate a string's or an array's indexes; `.forEach` and `.map` of a value that is no array are the TypeError V8 raises, naming the expression (`listOf`); a property read of null is a TypeError (`specGet`); `===` is strict (`strictIs`, `Value.Strict`), a property key is `String(v)` (`specText`), and a read finds the members of the built-in prototypes (`jsval.Member`: `[1, 2].fill` is a function, so an encode block given as an array never receives the `fill` default).
- **A value reference is upstream's generated source.** vega-parser turns each encode entry and production rule into JavaScript source and compiles it; the engine writes the same source (`encode_source.go`) and parses it for every reference, so a reference fails where upstream's does (`"mult": "x"` is the code `*x`, a signal reference; `["a", "b"]` is `nullnull`). A reference whose members have the documented types is evaluated by the engine's closures, which give the same result; any other by the source itself.
- **Signal handlers are parsed whole.** The event selector (a port of vega-event-selector), the stream specifications, their filters and the update are parsed as upstream parses them; only the handlers whose source is another signal or a scale fire in a static render. What the view does as it registers a view event listener is reproduced (an event named after an `Object.prototype` member fails).
- **The runtime follows the same rule** where a value of an unexpected type reaches it: fields of any type split as vega-util's `splitAccessPath` splits them (`jsval.SplitAccessPathOf`); accessors, keys and comparators are cached per context by their text, as vega-runtime's `ctx.fn` is; a mark type given as a list draws as that type with every `=== 'group'` false (`scene.Mark.LooseType`) and an unknown type fails where it is bounded and drawn; the view size of a width or height signal that is text concatenates as `view._viewWidth + padding` does; an object holding a `toString` member of its own has no primitive value (`TypeError: Cannot convert object to primitive value`), wherever it is printed or converted; a generator a scene calls while it is written (a shape's expression) ends the render with its exception.
- **`TestVegaTypeConfusionMatchesNode` is the guard** (`vgtypeconfusion_oracle_test.go`). It mutates one value of a Vega corpus specification (the `vg-fixtures`, `vg-gallery` and `regress-vg` sets, the specifications whose unmutated comparison is ok): a value of another type, a value derived from the one replaced (`[v]`, `[[v]]`, `String(v)`, `Number(v)`, `[...v, null]`), or a key renamed (to `"undefined"`, `""`, `"__proto__"`, `"constructor"`, `"toString"`, `"hasOwnProperty"` or a case-mapped spelling); it renders the mutant here and in node and requires an error exactly where node throws and otherwise an SVG equal as the corpus comparison holds them. An engine panic is never agreement; a render stopped at one of the engine's bounds (ErrLimit, the timeout) is counted, not compared (ADR 0005). A mutant node does not answer in time is rendered and counted, so that an engine panic is not hidden; one that ends node (V8's heap exhausted by an input upstream does not end on, such as a force at an infinite position or a density of infinite steps) when a fresh process asked the same is upstream's failure, logged with the reason node gave, and the engine must fail on it too or stop at a bound. Each divergence found becomes a mutant in `testdata/vgtypeconfusion`, which `TestVegaTypeConfusionRegressionsMatchNode` replays. The search runs nightly with a new seed (the `vgtypeconfusion` job of `.github/workflows/fuzz.yml`).

### Consequences

- **A behaviour change:** Vega specifications upstream rejects now fail (fewer successes), and some the engine refused now render.
- New parser or runtime code that reads a specification value must read it as upstream does; the helpers above are the place for it.
- Vega's runtime has its own JavaScript-semantics corners the differential keeps finding (values of unexpected types in transforms, scales, guides, item properties); the regression directory records each class fixed (`testdata/vgtypeconfusion`, 400-odd mutants, each the smallest witness of a class, each seen failing before its fix), and the report of each search lists what remains.
- **Where the search stands (2026-10-19).** The default sample (seed 1, 1,500 mutants) and seeds 7, 31, 47, 61, 73, 91 and 97 (20,000 each) show only the differences listed next, and each helper's own searches of one part of a specification (data, transforms, scales and encoding, marks and view, prototype-named keys; seeds 11 to 16, 21 to 23, 41 to 44, 81, 82, 101, 102) ended at the same list.
- **What is not matched, and why.** Each is a difference the differential reports on this host and the engine does not close:
  - *Platform arithmetic.* `Math.pow` is the C library's, glibc's in `internal/jsmath`; macOS's differs in about 0.2% of arguments, in the last place (`pow(2*sizeFactor, 3.5)` of the watch face with a one-pixel height is a tie between two doubles: glibc's and the engine's is the one `7.386311749264596e-9`, macOS's the other), so the nightly on macOS can report a stroke width or an angle of a mutant that is one unit off. `internal/jsmath` is bit-exact with V8 on arm64 ([floating-point parity](../design-rules.md#floating-point-parity)), where the Go compiler and V8 both fuse multiply-adds; the oracle on an x86-64 host computes some `Math.sin`, `Math.cos` and `Math.atan2` results one unit in the last place differently. A beeswarm or force-directed layout amplifies that (77 nodes, a chaotic simulation), and a trail mark's arc flag turns on it (an exact semicircle). The groups are `forces` and `xfocus` mutants of the beeswarm specifications and `step` of the trail mark; with the force's `Math.sin` made unfused all 77 starting positions equal x86-64 node's. The owner kept the engine on arm64's V8 (2026-10-20), so the nightly differentials run on the macOS arm64 runner, where these groups do not occur. Three classes do occur there, and are the only differences the nightly is expected to report: macOS's `Math.pow` above, the label placement on a sliver below, and text measured at a font size past the engine's clamp (below; its first nightly mutant was `labelFontSize` 1e308 on a legend, seed 20750).
  - *Label placement on a sliver.* (It surfaces in the mutants too: a text mark whose `encode` is lost has only empty labels, whose bounds are points, and the same trend line flips the anchor of one of them; with the line drawn 3 px wide, or not avoided, engine and node agree.) The `label` transform decides on a bitmap of the marks to avoid; for a 1-pixel line (`labeled-scatter-plot`'s trend line) cairo's scan converter sets 15 pixels the engine's four-fold supersampling does not, and the engine sets 10 cairo does not, which flips the anchor of one label in about 1,100. A bit-exact port of cairo's stroker and scan converter for every mark type is the only fix.
  - *How the nightly treats them.* The Vega differential counts and logs these two classes instead of failing on them, and only when the mutant confirms the class (`vgknown_oracle_test.go`). A label placement difference is one when every site of it is a text item's `text-anchor`, `transform` or `opacity`, and the mutant agrees with node once its label transforms avoid nothing. A `Math.pow` difference is one, on darwin only, when every site of it is an attribute holding one number, and the two values are adjacent doubles. A font-size difference is one when every site of it is a text element's text, the two sides are truncations of one text (one, its ellipsis dropped, begins the other), and the engine's document sets a font size past the 65,536 px clamp. Any other difference fails as before, as does one with more sites than the comparison lists. A label difference that has a cause beyond the avoided marks' bitmap still differs without them, and a 1-pixel offset planted in the label transform was reported, not classified.
  - *Font sizes beyond 65,536 px.* The engine clamps a font size there (a safety control, `maxSizePx`); node-canvas measures sizes past about 390,000 px (and `Infinity`, `1e308`) as FreeType and Pango overflow noise that depends on the host's float-to-integer conversion (a mutant's view with a `1e308` label font was 2,097,163 px wide in node on x86-64 Linux and 224 on the macOS arm64 runner), so a text `limit` or a view size that depends on such a width differs, and differs between hosts. The layout around an infinite size is matched (`0 * lineHeight` is `NaN` in `multiLineOffset`, so an axis title's offset is `NaN`, as upstream's).
  - *Process history in the oracle.* node-canvas keeps the font it had when a font string is rejected, and d3-geo keeps module-level state across calls. The engine models both as a fresh process would see them (the first measurement of a render starts from the default font; the state of the area, bounds and centroid streams lives in the view and starts as it does in a new process), and the oracle (`testdata/oracle-node/oracle.mjs`) now replaces its process after a request that could leave such state (a rejected font, `geoArea`/`geoBounds`/`geoCentroid`/`geoLength`, a `__proto__`) or whose canary render differs from the startup one, so a recorded answer does not depend on the order of the requests. The font a rejected string leaves behind is the canvas's initial one, `10px sans-serif`; left to the canvas that name resolves through the host (Pango's font map: a macOS system font on macOS, so a label the engine truncates to "t~" node truncated to "thr~" there, and a title box a pixel wider or narrower), so the oracle gives every canvas context, as it is made, the font the engine means by that string (the default family, DejaVu Sans here), maps the family list of every font string by the engine's pattern (`canvasFontFamilyRe`, all the units node-canvas reads, either case, no family at all), and answers `oracleErr` for a string the canvas accepts that the pattern did not map, so no accepted font resolves through the host.
  - *Prototype pollution through data* (not reproduced by decision, 2026-10-20: it is upstream changing the prototypes of the process's objects, which no chart relies on, and modelling it would make every plain-object lookup of a render consult a polluted chain). Where upstream assigns into an inherited member (`flows["__proto__"] = sf`, `group[j-1] = t` on a prototype method) it changes the prototype of a plain object or of `Object.prototype` itself for the rest of the process. The first-run behaviour is reproduced (a facet or a data join keyed `__proto__` opens a subflow or item per tuple and keeps none; `countpattern`, `pivot`, `window`, `nest`, `impute`, `lookup`, `indata`, `treePath` and `treeAncestors` find or miss an inherited member as upstream does). Not modelled: a read of `datum.__proto__` (the engine answers undefined, upstream `Object.prototype`), the reruns and `clean()` of a facet or join keyed `__proto__`, a tree whose node id is `__proto__`, an `aggregate` cross over an array whose text is `__proto__`, and the pollution `impute` makes of `Object.prototype` (node's `finalize` then throws "Spread syntax requires …iterable[Symbol.iterator] to be a function"). A pivot whose `value` is `__proto__` reads an inherited member as the accessor (node prints `NaN`, the engine nothing).
  - *A wordcloud whose `text` is a list.* Upstream writes a word made from an array of words as the array's text, and where the array comes from a signal's function it is the source text of vega-util's accessor closure; the engine throws instead. Exotic (4 specifications of thousands of mutants), and the closure's source is node's, not something a chart can rely on.
