# Limits and timeouts

Specifications are untrusted input: a 200-byte spec can ask for a billion rows. Every render is therefore bounded in time and in the work and memory it may use, and a render that would exceed a bound fails, with an error wrapping `aster.ErrLimit` (or `context.DeadlineExceeded` for time), instead of exhausting the host. The defaults are far above what real charts need. Tune them with two options on `New`:

```go
c, err := aster.New(
    aster.WithTimeout(10*time.Second),  // whole call, every stage; default 30 s; <= 0 disables
    aster.WithMemoryLimit(256<<20),     // replaces the memory budgets below; default: the fixed defaults
)
```

`errors.Is(err, aster.ErrLimit)` tells a spec that asked for too much from one that is broken. The message names the bound ("data rows 4000000 exceeds the limit of 1000000").

## WithTimeout

It bounds one call from start to finish: compiling, evaluation, text shaping, writing SVG, PNG and PDF. A run of text stops partway when the time is up. The error wraps `context.DeadlineExceeded` and names the stage. Default 30 s; zero or negative means no timeout (the CLI's `-timeout 0`). Slow but legitimate charts are mostly geographic: projections of detailed maps, and faceted maps.

Parsing JSON, the specification's and loaded data's, checks the deadline as it reads: about every 16 KiB of text, inside a long string, run of white space or number literal too (a number literal of more than 800 bytes is converted from its first 800 significant digits, a sticky digit and its exponent, which round exactly as the whole literal does). Both are also bounded by size, by the parsed-JSON budget below (1 GiB, or `n/2` with `WithMemoryLimit(n)`), the specification also by its size row and loaded data by the loaded-bytes allowance. Decoding an image (bounded by its bytes, 32 MiB, and its pixels) cannot be interrupted either, but it is fed its bytes a few at a time with the deadline checked between them: a PNG makes at most about a quarter of a million pixels between two checks, however well it compresses. A JPEG or GIF can decode longer stretches, bounded only by its bytes and pixels (a progressive JPEG is put together after its last byte is read). What is done with a decoded image (converting its pixels, halving it for a small drawing, writing it into a PDF) checks the deadline every 65,536 pixels. Parsing SVG given to `SVGToPNG` checks it as it reads, about every 16 KiB, and matching its style sheets about every thousand steps of the matching work below (a step is a lookup or a comparison of a few bytes: an element's attributes and classes are indexed once). So does every pass the rasterizer makes over a filter region (each primitive's, every pass of a blur, a conversion between colour spaces, the copy of the result) and over a layer it composites, a mask it applies or two clips it intersects; the buffers a filter allocates are zeroed by the runtime between two checks.

`WithTimeout` bounds every call; `WithContext(ctx)` bounds one call by `ctx` as well (its cancellation and its deadline), which a server uses to stop a render whose client has gone away. A call whose context ends fails with the context's error and returns no output.

## WithMemoryLimit

It is not a heap cap: Go has none per call. It is converted into the budgets below, each charged *before* the allocation it pays for. With `WithMemoryLimit(n)`, each budget becomes the formula in the third column, which **replaces** the default: a large `n` raises the bounds that have no ceiling as a small one lowers them (the table gives each one's floor and ceiling), and the bounds that are none by default become bounded. `WithMemoryLimit(0)`, the default, keeps the defaults.

The SVG output bound is the size of the document, checked by the writer as it writes: inside an item as well as between items (a text of a million line breaks is a million `<tspan>`s, a path or a custom symbol is drawn into its numbers, a value is escaped into entities), in the `<defs>` written after the marks, and for marks without items. Past it the call fails with `ErrLimit` without finishing the document; the path a generator draws is stopped at the room left in it, and the deadline is polled as the output grows. A document too large for the reusable buffer is returned without a copy of it.

A filter region past its bound, and SVG input past its bytes, elements or style sheet bounds, fail the call rather than draw the element or the document in part. The rasterizer's canvas memory is every pixel buffer alive at once: the canvas, offscreen layers (opacity groups, masks, filters), clip coverage maps (one per clipped element, held while it draws) and every result and scratch buffer of a filter chain. An offscreen layer holds the pixels drawn into it, not the canvas's: it grows to hold what is drawn, so a small opacity group costs little on a large canvas. The `label` transform draws the marks it avoids at four samples a pixel each way (fewer on a layout of more than 1 Mi pixels) without a canvas of the samples, keeping one bit for each pixel of the layout and the layers its marks are drawn through, under this bound. Its path points are the geometry the elements being drawn hold: parsed path data, flattened polylines, stroke outlines and scan-converter edges (an edge counts as five points); geometry wholly outside the canvas or clip is not built.

Data rows are the tuples alive at once, each held by the operator that made it: a data set's loaded or inline rows, the rows a transform makes (an `aggregate`'s groups, a `sequence`, a `fold`), the copies a derived data set hands on, the rows `modify()` inserts, a prefacet's cells. A transform that runs again replaces what it held, so a signal write is not charged twice, and an operator that only passes rows on (a `filter`, a sort) holds none ([ADR 0012](adr/0012-rows-held-by-their-maker.md)). With `WithMemoryLimit`, a row is also weighed: one that outweighs 512 bytes (many fields, long strings) counts for more than one, so the rows bound their memory, not just their number. Delimited text (CSV, TSV, DSV) is charged a row at a time, before the row is made.

Loaded bytes are the data and images one call loads, together. Data loads one data set at a time, each Loader call given what is left. The images PNG and PDF output fetch, eight at a time, share the call's allowance as they read: `HTTPLoader` and `FileLoader` (and a Loader of your own that wraps them, passing on the context) charge it 32 KiB at a time as they read, before they read on, so the fetches together stop where it ends, each having read at most one 32 KiB chunk past what it charged (the chunk refused). What a Loader of your own returns without charging it is charged when its `Load` returns, before the image is decoded. Bytes charged stay charged, those of a fetch that then fails included (a body cut short, an image over its 32 MiB), so a call fails with `ErrLimit` exactly when the bytes its loads read add up to more than the allowance, whatever order the fetches ran in, and an image that fits is never refused because others were in flight.

The last row is the ledger's byte meter ([ADR 0010](adr/0010-bounds-charged-where-work-happens.md)): one per call, spanning every stage, charged by the code that allocates, before it allocates, for memory the rows above do not count. The rows above each bound their own kind of memory and keep their own semantics (rows are replaced as data flows, canvases come and go); an allocation is charged to one meter, its own if it has one and the ledger's otherwise, so together they stay within a small multiple of `n`. Today the ledger is charged for the regular expressions an expression or `countpattern` compiles (literals as the expression is parsed, patterns made from strings as they are made; the parse and then the compiled form, each before it allocates), parsed path data (custom symbols and `path` marks), the SVG the rasterizer draws (its text, and the tree it parses to: nodes, a run of text a node, attributes, children lists, ids, decoded entities and style sheet text, each charged as it is built), the rules of its style sheets and what they give each element, the characters and glyphs of its text as they are laid out (given back when the element is drawn), the images it decodes (before it decodes them, once per distinct image, as much as the decoder allocates: a progressive JPEG keeps its coefficients, four bytes a sample, and an interlaced PNG decodes each pass apart), the pattern tiles, colour glyph bitmaps, gradients, glyph outlines and SVG glyph documents it keeps for reuse (each cache also bounded by its own bytes; an SVG glyph document is charged as it is inflated and parsed), the maps and buffers of PNG quantization and recoding (quantization's colour maps as it finds the colours), the pixels of a PDF's images and the streams made of them, a PDF's content stream, its ExtGStates, forms and cached glyphs, the font programs cut out for it, the GeoJSON a TopoJSON document decodes to (every reference to an arc makes its positions anew) and the points of a graticule, the text of axis and legend labels (whose length a format's width and a locale choose), the call's table of the image and link URLs it resolved through the Loader, the tuple list each dataflow operator outputs (a filter's or a sort's list of the rows it passes on, which the data rows do not count; given back when the Vega run is over), what the expression environment keeps or hands an expression (512 bytes for each `geoShape()` and `pathShape()` generator, the lists of a `modify()` change set from the call that records them until they are applied, 24 bytes an element for an array of more than 256 that `domain()`, `range()`, `gradient()`, `invert()`, `treePath()`, `treeAncestors()` or `data()` of a mark makes; the tuple view of each item that `data()` of a mark, `item.mark.items` or a mark fed by another mark's items reads, and the array of a mark's items, each kept for the run), the Vega-Lite compiler's strings and copies (below), and whatever a stage adds to it as it is bounded. A regular expression search holds for backtracking at most what the ledger has left: goecma262 allocates that memory as it searches, so the ledger bounds it rather than counts it ([ADR 0014](adr/0014-library-memory-bounded-by-ledger-room.md)). Its default is about fifteen times what the heaviest chart of the corpus holds at its peak (130 MiB, rendered to SVG, PNG and PDF).

The transforms charge the ledger for what they hold that is not rows: the rasters of `kde2d` and density `contour` (two float32 and a float64 raster a group, and the grid each group outputs), contour rings and their output geometry, the triangulation of `voronoi`, the running state of an `aggregate` or `pivot` cell for each measure, the `values` arrays of a `window`, the bitmaps and masks of `label`, and the board of `wordcloud`. A `density` reserves its samples as rows before drawing them, and `countpattern` its distinct tokens. Where upstream's algorithm would not end, aster refuses the input with `ErrLimit` ([ADR 0011](adr/0011-faithful-output-free-algorithm.md)): a `voronoi` whose coordinates leave the triangulation's links cycling, and a `pack` whose front chain does not close.

The ledger also meters the call's *work*: a loop whose trip count the input controls charges each step, and charging polls the call's context, so `WithTimeout` and `Close` stop that loop, wherever it is. Work is counted, not capped: time is bounded by `WithTimeout`.

Vega-Lite views are the views a Vega-Lite specification describes, weighed before the compiler builds any: every unit, layer, concatenation and facet, and a repeat's spec once per repeated value (per combination of its `row`, `column` and `layer` values, nested repeats multiplying). A 1 KB specification of four nested repeats describes 810,000 views; past the bound it fails with `ErrLimit` naming the weight. A unit view weighs more for what it is given to compile: one more per selection a view above it declares (each is copied into every unit below it: 1,000 selections over 400 repeated views made a 37 KB specification that was OOM-killed), and one more per 4 KiB of specification text it compiles, its own (its inline data aside) and what it inherits (a layer's shared encoding, the selections it receives, the config and theme), which its expressions copy (a 200 KB number format in the config, written into the axes, tooltip and description of 256 repeated views, made 257 MB). The heaviest chart of the corpora weighs 51 views.

The compiler charges its memory to the ledger (the "memory charged to the call's ledger" row): each string it builds that the specification sizes, before it is built (an expression that guards every prefix of a long field path, a label expression whose format's `` $` `` pattern copies the text before each match, a format expression per tooltip field), the copies it makes of the specification and of parse and field sets, and the names and literals it writes per view and selection. A compilation past what the ledger has left fails with `ErrLimit` before it allocates the string or copy that would pass it; its charges are kept until the call ends (the compiled specification holds most of them). The heaviest chart of the corpora charges 1.1 MiB.

On 32-bit platforms a count or size past what an `int` holds saturates at 2 GiB − 1 rather than wrapping; that only matters for limits above 8 GiB.

## Choosing a limit

- **Trusted specs** (your own charts): keep the defaults, or raise the timeout for heavy maps.
- **Untrusted specs** (a service that renders what users send): set `WithMemoryLimit` to what one render may hold, for example `256 << 20`, and a timeout that fits your request budget. Don't use a broad `HTTPLoader`; see [security.md](security.md). Run renders under a concurrency limit of your own: the bounds are per call, and ten parallel calls can each use their budget.
- A render that fails with `ErrLimit` on a chart you trust: raise `WithMemoryLimit`. For example `2 << 30` allows about 4M rows. Or raise the Loader's cap if the error names a response or a file.
